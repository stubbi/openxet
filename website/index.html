Large-file storage that uploads only what changed.

openxet is Xet storage you run yourself. Every upload sends only the chunks your server doesn’t already have, and Hugging Face’s own client library, hf_xet, works with it unmodified.

How it works

An edit costs the edit, not the file.

Xet cuts each file into chunks of about 64 KiB, at boundaries set by the content. Before an upload, the client asks your server which chunks it already has and sends only the rest.

  • Boundaries follow the content, so an edit only disturbs the chunks around it
  • Chunks match against every file on the server, not just the last version
  • Downloads put the chunks back together into the whole file, byte for byte

Use cases

What your files actually share.

Deduplication pays where versions share content, and only there. These are measured pairs of real files, models, data, source and archives alike: how much of each new version was new.

  • Appended logs and growing tables reuse most of the last version
  • A source tree’s next release still shares a good part of its archive
  • Compressed, encrypted or fully retrained files share almost nothing, and we say so

Compatibility

One store, every client.

S3 and Git LFS send every version whole. The Hugging Face Hub deduplicates, but only on Hugging Face’s servers. openxet is Xet storage you run, and the stock client talks to it unchanged.

  • Files are standard Xet: the stock client reads back what openxet stores
  • Your platform signs scoped tokens for its users and calls the storage API
  • Apache 2.0 and a data directory you own: leave whenever you like

Security

Security you can check, test by test.

Each security requirement in the design has a named test that runs in CI. These are the ones that apply to the storage server today.

  • No telemetry unless the operator opts in
  • Credentials are never echoed in responses or written to logs
  • Report a weakness privately through the security policy

  • Verified before stored

    Uploads are checked against the stored chunks before any file is registered.

    shard_with_missing_xorb_rejected

  • Dedup without leaks

    Answers are HMAC-keyed, never raw hashes; tenants can be isolated.

    dedup_response_hmac_keyed

  • No anonymous reads

    Reads need a credential, and every transfer URL is signed for one byte range.

    signed_url_bound_to_range

  • Writes survive a crash

    An acknowledged upload is still there after the server is killed.

    acked_write_survives_sigkill

FAQ

Before you decide.

Looking for a technical detail? Start with the documentation.

Is openxet part of Hugging Face?

No. openxet is an independent open-source project that implements the Xet protocol published by Hugging Face. It is not affiliated with or endorsed by Hugging Face.

Can I use hf upload or Git with it today?

Not yet. Today hf_xet and the openxet command line upload and download against the storage server. The Hub API, hf upload, huggingface_hub, Git and LFS are the next milestone, in development now. Follow the changelog or watch the repository on GitHub.

How much will I save?

As much as your versions share. Appended logs reuse most of the last version; compressed archives and consecutive training checkpoints reuse almost nothing. See the measured pairs above and test with your own files using the quickstart.

What if I want to leave?

Self-hosted, your files sit in the standard Xet format in a directory you own, and the code is Apache 2.0, so you can keep running it without us. Export terms for hosted openxet will be published before launch.
