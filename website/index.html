OpenXet · open source · Apache 2.0

Git for large files. Only the changes upload.

OpenXet is open-source Xet storage for large files and datasets, in repositories and buckets. git push and hf upload send only the chunks your server doesn’t have, not the whole file as Git LFS does. Run it yourself or on openxet.com.

Repositories

Git and Hugging Face repositories on your server.

Host repositories on OpenXet, or keep the code on GitHub, GitLab or Gitea and put the large files here. Hugging Face’s own tools work without changes. OpenXet is an independent project, not part of Hugging Face.

  • git clone, git push and git-xet against OpenXet or your existing Git host
  • hf upload, hf download and huggingface_hub, pointed at your server
  • model and dataset are labels like any other, and you can add your own

Xet

A 1 MiB edit uploads about 1 MiB.

Xet cuts each file into chunks of about 64 KiB, at boundaries set by the content. Before an upload, the client asks your server which chunks it already has and sends only the rest.

  • Boundaries follow the content, so an edit only disturbs the chunks around it
  • Chunks match against every file on the server, older versions included
  • Downloads put the chunks back together into the whole file, byte for byte

Use cases

How much real files share between versions.

Deduplication only helps when one version repeats content from the last. We measured pairs of real files (a log, a table, a source release and a model checkpoint) and counted how much of each new version was new.

  • Appended logs and growing tables reuse most of the last version
  • Compressed, encrypted or fully retrained files share almost nothing

Buckets

Buckets for what isn’t versioned.

Checkpoints, logs and agent outputs change too often to commit. A bucket stores them under keys you can overwrite, with the same deduplication and no Git history.

  • The last write to a key wins; object versioning is optional
  • Buckets take labels such as checkpoint and eval-logs, as repositories do

Self-hosting

Runs on the storage and sign-in you already have.

OpenXet is one binary. Nodes keep no state, so you scale by adding more of them, and the object store holds every byte; the index can be rebuilt from it.

  • S3, GCS, Azure, MinIO or local disk, with Postgres or SQLite for the index
  • Sign-in through your OIDC provider or webhook; OpenXet never owns users
  • An audit log, data residency and a full export, so you can leave at any time

Platforms

Embed it in your own product.

Platforms run OpenXet behind their own names and interface. Your users talk to your product, and your product decides who may read and write.

  • OpenXet asks your authorizer webhook before each read or write
  • Scoped, signed tokens per user, repository or bucket
  • Per-tenant metering for your own billing

Agents

Scripts and agents use the same commands.

Add --json to any command for one object with a versioned schema. Errors carry a code and a hint, and openxet mcp serves the same operations to MCP clients.

  • Stable exit codes, documented per error code
  • Delegated tokens narrower than yours; approval gates for destructive actions
  • The audit log records an agent’s actions under the person it acts for

Each security requirement has a named test.

The tests run in CI on every change. There is no telemetry unless the operator turns it on.

  • Verified before stored

    Uploads are checked against stored chunks before any file is registered.

    shard_with_missing_xorb_rejected

  • Keyed dedup answers

    Answers are HMAC-keyed, never raw hashes; tenants can be isolated.

    dedup_response_hmac_keyed

  • No anonymous reads

    Every transfer URL is signed for one byte range and one scope.

    signed_url_bound_to_range

  • Writes survive a crash

    An acknowledged upload is still there after the server is killed.

    acked_write_survives_sigkill
