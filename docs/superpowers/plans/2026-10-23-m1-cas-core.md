# M1: CAS core Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** `openxet serve` runs a storage-only Xet CAS on SQLite and local
disk. Stock `hf_xet` 1.7.0 and openxet's own client upload, dedup and
download through it unmodified, and every M1 security test passes.

**Architecture:** One binary. `openxet-cas` is an axum router over three
seams:
- `openxet-index`: an async trait, implemented on SQLite
- `openxet-storage`: the bucket (here, a durable local-disk store)
- `openxet-auth`: static tokens and signed CAS tokens

All format work stays in `openxet-protocol` (ADR 0001). The client core
wraps `xet-data` in `openxet-client` (ADR 0006). The bucket is written
before the index, so the index can be rebuilt from it. Downloads use
openxet-signed, range-bound URLs served by the transfer route (ADR 0002,
mode b).

**Tech Stack:**
- Rust 1.97 (edition 2024)
- tokio, axum 0.8, tower-http
- sqlx 0.8 (SQLite, runtime queries, embedded migrations)
- jsonwebtoken (EdDSA), hmac and sha2
- `xet-core-structures`, `xet-data`, `xet-runtime` and `xet-client`, all
  `=1.7.0`
- cargo-fuzz, criterion
- pytest + uv with `hf_xet` 1.7.0 (compat)

**Spec:** `docs/superpowers/specs/2026-10-23-openxet-design.md` (§3, §5.2–§5.6,
§5.9, §7, §7.1, §8, §10.8, §12 M1). The wire contract is
`docs/research/S10-cas-wire-contract.md`, which is binding for every route
in this plan. S5, S6 and ADRs 0001, 0002 and 0005 also apply.

## Global Constraints

**Protocol**
- Use `xet-core-structures`, `xet-data`, `xet-runtime` and `xet-client` at
  exactly `=1.7.0`. Dependabot ignores them (ADR 0001).
- `xet_core_structures::…` is used only in `crates/protocol`. `xet_data`,
  `xet_runtime` and `xet_client` are used only in `crates/client`
  (ADR 0006).
- `#![forbid(unsafe_code)]` in every crate. The only exception is the
  `fuzz/` crate, which is outside the workspace.
- CAS routes are served at the origin root, HTTP/1.1, with uncompressed
  responses (S10 "Conventions").
- Unimplemented CAS routes, `/v1/xorb-grants/*` included, answer `404` and
  never `501` (S10 "Status codes and retries").

**Responses**
- Every response carries `X-Request-Id` (UUIDv7).
- Every HTTP error body is
  `{"schema":"openxet.error.v1","code","message","hint"}`. Content failures
  on `POST /v2/shards` go in the stream's `error` event, not in a status
  (S10 §4).

**Durability and privacy**
- Bucket first, index second. An acknowledged write is fsynced to disk and
  committed to SQLite (WAL, `synchronous=FULL`) before the response is
  sent (design §5.3, §5.9 req 7).
- Credentials never appear in logs, error bodies or response headers. The
  dev-mode startup banner on stdout is the single documented exception
  (design §7).
- No telemetry. `POST /v1/telemetry` answers `204` and is never read into
  a store or a log. Our client sets `telemetry.enabled = false`.

**Process**
- One branch and PR per task (`m1/tN-<slug>`), squash-merged.
- Commits use `git commit -s` with Conventional subjects and a component
  scope, and end with
  `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`.
- Disclosure rule R21/R26: no public text describes or hints at an
  unfixed third-party security weakness.
- TDD: show RED before GREEN. Never weaken a test to make a change pass.
- Every new CLI command has `--json` with a versioned schema, documented
  exit codes, and an entry in the agent leg (`JSON_COMMANDS`).

## Review Focus

These are the conditions most likely to hurt a user that the design
implies but no feature test exercises naturally. Each is pinned by a test
in the owning task.

1. **A retried write after a lost response.** `hf_xet` resends a whole
   xorb or shard after a timeout, even when the first attempt committed.
   It must succeed again with the same effect.
   - Pinned by `xorb_upload_retry_after_commit_succeeds` (Task 8) and
     `shard_upload_retry_after_commit_succeeds` (Task 9).
2. **Range edges.** A `Range` past EOF, a range that starts mid-chunk, and
   the empty file must download byte-exact, with `416` only when the
   start is at or past EOF.
   - Pinned by `reconstruction_range_edges` (Task 11) and the compat
     test `test_range_and_empty_file` (Task 14).
3. **The same xorb uploaded concurrently by two clients** must store one
   intact object and answer both.
   - Pinned by `concurrent_identical_xorb_uploads` (Task 8).
4. **A restart.** Data, the dev token and transfer URLs signed before the
   restart (within their lifetime) keep working.
   - Pinned by `restart_keeps_data_token_and_urls` (Task 12).
5. **A storage write failure** answers a retryable `5xx` and registers
   nothing. The index never points at bytes the bucket lacks.
   - Pinned by `storage_failure_registers_nothing` (Task 8) and
     `shard_storage_failure_registers_nothing` (Task 9).

## Decisions this plan makes (rulings, recorded in the ledger)

- **M1-R1. Frameworks.**
  - axum 0.8 on tokio (the design's default).
  - sqlx 0.8 for the index: one async API for SQLite now and Postgres in
    M3, using runtime queries so the build needs no database.
  - The local-disk store is openxet's own module, because `object_store`'s
    local backend doesn't fsync. `object_store` comes in M3 for S3, GCS
    and Azure behind the same `Bucket` trait.
- **M1-R2. CAS tokens are EdDSA (Ed25519) JWTs** (ADR 0007).
  - Claims: `{sub, scope, mode: "read"|"write", exp, iat}`, plus `kid` in
    the header.
  - Platforms sign them with standard JWT libraries in any language;
    openxet verifies them against a configured public key set. Static
    tokens are compared by SHA-256 in constant time.
- **M1-R3. Signed data URLs** take the form
  `{public_url}/v1/transfer/xorbs/{xorb}?range={start}-{end}&exp={unix}&sig={b64url}`.
  - `sig` is HMAC-SHA256 over `"xorb\n{xorb}\n{start}-{end}\n{exp}"`,
    keyed with the transfer key.
  - The request must carry exactly `Range: bytes={start}-{end}`. A
    missing `Range` header is a `400`; a different range, an expired URL
    or a bad signature is a `403`. These are the three properties of
    ADR 0002's probe.
  - Lifetime defaults to 60 min, with a 30 min floor.
- **M1-R4. Dedup responses are synthesized,** not reused uploaded shards
  (design §13 leaves this to the builder).
  - The response holds the most recently ingested xorb that contains the
    queried chunk and is visible to the caller. Its whole chunk table is
    keyed with a fresh random 32-byte HMAC key, and the footer's
    `shard_key_expiry` is now + 7 days.
- **M1-R5. The GC grace floor is 28 days.** Clients dedup against cached
  shards for 21 days (S10), and dedup keys live 7 days.
  - Design §5.6 changes its default from 7 days to 30, and `gc` rejects
    any value below 28 (the GC code itself is M4).
  - Errors for a missing referenced xorb tell users how to clear a stale
    client cache.
- **M1-R6. `GET /v2/file-chunk-hashes` is M6** (our client's `sync`
  needs it).
  - No stock client calls it (S10), and upstream's builder lives in
    `xet-client`, which would need an ADR 0006 extension on the server
    side.
  - Until then it answers `404`. The design's milestones list it under M6.
- **M1-R7. Metering (§5.7) moves to M4,** with the admin API. No
  milestone listed it. The design milestones are edited.
- **M1-R8. Scale and amplification.**
  - Xorb validation runs in `spawn_blocking` behind a semaphore of
    `available_parallelism()` permits, which bounds concurrent
    decompression work.
  - Double decompression on accept stays: it is bounded at 2 × 1 GiB per
    xorb and costs less than reimplementing footer serialization
    (ADR 0001). The Task 16 benchmark records the cost.
- **M1-R9. The client version floor is `hf_xet` 1.7.0,** the version
  verified in S6 and S10.
  - The compat suite pins 1.7.0. The nightly job also runs the newest
    release and pre-release; `hf-xet` 1.8.0.dev0 exercises the grant
    `404` fallback.
- **M1-R10. Default bind is `127.0.0.1:8080`,** which is also `hf_xet`'s
  default CAS endpoint (S10 "Auth"). `--port` overrides it.

### Task 2: Protocol additions for the server

**Files:**
- Modify: `crates/protocol/src/xorb.rs`, `crates/protocol/src/shard.rs`, `crates/protocol/src/lib.rs`
- Create: `crates/protocol/src/dedup.rs`, `crates/protocol/tests/server_formats.rs`

**Interfaces:**
- Consumes: `StoredXorb`, `UploadShard`, `XorbChunkLookup` (M0).
- Produces:
  - `StoredXorb::chunk_offsets: Vec<u32>`: `n + 1` entries. Entry `i` is
    the byte offset of chunk `i`'s header in `StoredXorb::bytes`, and the
    last entry is the end of the chunk section. So the end-inclusive
    `bytes` range for chunks `[a, b)` is
    `chunk_offsets[a] ..= chunk_offsets[b] - 1`.
  - `pub fn stored_shard(shard: &UploadShard, lookup: &impl XorbChunkLookup) -> Result<Vec<u8>, ProtocolError>`:
    a footer-less shard re-serialized with upstream's serializers. Its
    file info carries segments, verification and sha256, and its CAS info
    is built from the server's chunk tables for the referenced xorbs
    only. It is what the bucket stores (S6 "What gets stored").
  - `pub fn shard_hash(bytes: &[u8]) -> MerkleHash`: upstream's data hash
    of the stored bytes.
  - `pub fn is_dedup_eligible(chunk: &MerkleHash) -> bool`: the spec
    rule, via upstream's `hash_is_global_dedup_eligible`.
  - `pub fn dedup_shard(xorb: &MerkleHash, chunks: &[(MerkleHash, u64)], key: MerkleHash, expiry_unix: u64) -> Result<Vec<u8>, ProtocolError>`:
    a footered shard with an empty file-info section and keyed chunk
    hashes, built with `MDBShardInfo::export_as_keyed_shard_streaming(.., include_file_info = false, ..)` (S10 §2).

- [ ] **Step 1: Write the failing tests** in `tests/server_formats.rs`:
  - `chunk_offsets_frame_every_chunk`: for the reference xorb and the
    hf_xet capture, `chunk_offsets.len() == n + 1`, and
    `read_xorb_chunks(&bytes[off[a] as usize..off[b] as usize])` yields
    exactly chunks `a..b`, for `(a, b)` in `[(0, 1), (0, n), (n - 1, n)]`.
  - `stored_shard_round_trips`: `read_upload_shard(stored_shard(s, lookup))`
    equals `s` with `xorbs` reduced to the referenced xorbs, and
    `verify_shard` passes on it for the hf_xet capture.
  - `stored_shard_is_deterministic`: two calls give identical bytes and an
    identical `shard_hash`.
  - `dedup_shard_hides_raw_chunk_hashes`: no raw chunk hash of the xorb
    appears anywhere in the output bytes. Upstream's footer parser reads
    `chunk_hash_hmac_key == key` and `shard_key_expiry == expiry`, and the
    file-info section is empty.
  - `dedup_eligibility_matches_upstream`: over 10^4 seeded random hashes,
    the result equals the spec formula (last 8 bytes as LE u64,
    `% 1024 == 0`).
- [ ] **Step 2: Run** `cargo nextest run -p openxet-protocol -E 'binary(server_formats)'`.
  Expected: FAIL (compile errors on the missing items).
- [ ] **Step 3: Implement.**
  - Offsets come from the validated chunk walk (`pos` before each header;
    footer excluded).
  - `stored_shard` and `dedup_shard` compose upstream's shard types
    (S5's table names them). No format logic of our own.
- [ ] **Step 4: Run** the full protocol suite. Expected: PASS, with
  clippy and doc clean.
- [ ] **Step 5: Commit** as `feat(protocol): chunk offsets, stored and dedup shards for the CAS`.
